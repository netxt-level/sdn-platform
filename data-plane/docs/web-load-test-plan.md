# 웹 서비스 부하 테스트 환경 계획

- 상태: 계획
- 대상: 격리된 `sdn-lab` VM의 Mutillidae II 웹 서비스
- 사용자 기준: 정상 100명, 피크 300명, 스트레스 500명

## 목적

평범한 중소 규모 게시판의 사용자 행동을 재현해 웹 애플리케이션 한계와 SDN
경로 한계를 분리해서 측정한다. 먼저 링크 병목이 없는 환경에서 웹과 DB의 기준
성능을 구하고, 이후 제한된 링크에서 혼잡 감지, 경로 변경, 장애 복구를 검증한다.

이 계획의 동시 사용자 수는 실제 Mininet 호스트 수가 아니라 부하 도구가 `h1`
네임스페이스에서 유지하는 독립적인 HTTP 세션 수를 의미한다. 공격 트래픽을
발생시키는 `h3`는 이 사용자 수에 포함하지 않는다.

Mutillidae는 보안 실습용 애플리케이션이며 성능 기준 애플리케이션이 아니다.
따라서 결과는 일반 웹 서비스의 절대 성능이 아니라 현재 실습 환경의 기준선과
구성 변경 전후의 상대 비교에 사용한다.

## 배치 구조

```text
h1(load generator) ─┐
h2(admin traffic)  ─┼─ s1 ─┬─ s2 ─┬─ s4 ─ web(10.0.0.100)
h3(attack traffic) ─┘      └─ s3 ─┘              │
                                                   └─ Mutillidae / DB

s1 mirror output ─ sdn-sensor0 ─ Analyzer
Controller ─ Backend ─ Frontend
```

| 구성요소 | 역할 |
|---|---|
| `h1` | Locust 또는 k6 기반 정상 사용자 부하 생성 |
| `h2` | 관리자 조회와 저빈도 관리 요청 |
| `h3` | 이후 공격 시나리오 전용, 정상 사용자 집계에서 제외 |
| `web` | `10.0.0.100:80`으로 제공되는 Mutillidae 프록시 대상 |
| `sdn-sensor0` | OVS Mirror로 복제한 양방향 트래픽 캡처 |
| Analyzer | 패킷 요약, 트래픽 통계, 보안 이벤트 생성 |
| Controller | 경로, 포트 통계, Flow Rule 상태 관리 |

500명까지 한 VM에서 실행할 경우 최소 4 vCPU와 8GB 메모리, 권장 8 vCPU와
16GB 메모리를 할당한다. 부하 생성기의 CPU 사용량이 웹 서버나 Controller보다
먼저 포화되지 않는지 함께 확인한다. 모든 구성요소의 시간대는 동일하게 맞추고
결과에는 UTC 또는 타임존이 포함된 시각을 사용한다.

## 사전 데이터와 사용자 모델

동일한 조건을 반복하기 위해 테스트 시작 전에 다음 상태를 준비한다.

- 최대 500개의 테스트 계정
- 게시글 약 1,000개
- 조회 가능한 댓글과 검색 데이터
- 각 테스트 후 복원할 Mutillidae DB 초기 상태 또는 Docker volume snapshot
- 각 가상 사용자별 독립 쿠키와 HTTP keep-alive 세션

사용자 행동은 다음 비율을 기본값으로 한다.

| 행동 | 비율 | 설명 |
|---|---:|---|
| 목록 및 게시글 조회 | 60% | 목록 이동과 상세 페이지 조회 |
| 로그인과 세션 유지 | 20% | 계정 풀에서 사용자 선택 후 로그인 |
| 게시글 및 댓글 작성 | 15% | 테스트용 고유 데이터 작성 |
| 검색 및 기타 조회 | 5% | 검색, 사용자 정보 등 보조 기능 |

각 행동 사이에는 2~5초의 무작위 대기시간을 둔다. 모든 사용자가 동시에 같은
URL을 반복 호출하는 방식은 일반적인 사용자 행동과 다르므로 기본 시나리오로
사용하지 않는다. 테스트 계정은 한 실행 안에서 중복 로그인 충돌이 없도록
분배한다.

Mutillidae 응답 크기가 작아 링크 부하가 충분하지 않으면 동일 웹 호스트에서
100~256KB 크기의 정적 리소스를 제공하고 일부 조회 행동에 포함한다. 별도의
`iperf3` 트래픽을 웹 사용자 트래픽으로 간주하지 않는다.

## 부하 단계

| 단계 | 동시 사용자 | 증가 속도 | 유지 시간 | 목적 |
|---|---:|---:|---:|---|
| 준비 확인 | 5명 | 초당 1명 | 3분 | 로그인, 조회, 작성 동작 확인 |
| 워밍업 | 20명 | 초당 2명 | 5분 | 캐시와 연결 준비 |
| 정상 부하 | 100명 | 초당 5명 | 15분 | 일반 웹사이트 기준 측정 |
| 피크 부하 | 300명 | 초당 10명 | 15분 | 이용 집중 시간 측정 |
| 스트레스 | 500명 | 초당 20명 | 10분 | 최초 병목과 한계 확인 |
| 복구 확인 | 100명 | 500명에서 감소 | 10분 | 부하 감소 후 정상화 확인 |

정상 부하는 초기 상태에서 최소 3회 반복하고 피크 부하는 최소 2회 반복한다.
스트레스 테스트는 시스템 보호 기준을 넘기면 즉시 중단할 수 있다. 단계별 독립
결과가 필요하면 DB와 컨테이너 상태를 복원한 뒤 각각 실행하고, 전체 회복 특성이
필요하면 위 단계를 하나의 연속 실행으로 수행한다.

## 네트워크 프로필

### 프로필 A: 애플리케이션 기준선

- 링크 대역폭: 100Mbps
- 링크 지연: 5ms 이하
- 인위적 패킷 손실: 0%
- 테스트 중 링크 장애 없음
- 테스트 중 수동 경로 변경 없음

웹 서버, DB, Mutillidae TCP relay 또는 부하 생성기가 먼저 포화되는 지점을
측정한다. 이 결과가 없으면 이후 링크 제한 테스트에서 발생한 오류를 웹 서버
문제와 네트워크 문제로 구분할 수 없다.

### 프로필 B: SDN 경로와 혼잡

- Primary 및 Backup 링크 대역폭: 10Mbps
- 링크 지연: 5~10ms
- 인위적 패킷 손실: 0%
- 혼잡 임계값: 70%
- 정상 부하 100명과 피크 부하 300명을 각각 실행

프로필 B에서는 다음 이벤트를 하나씩 독립적으로 수행한다.

1. 정상 상태에서 Primary 경로와 포트 사용량을 기록한다.
2. `s1-s2` 또는 `s2-s4` 링크를 비활성화한다.
3. Backup 경로 전환 시각과 손실 구간을 기록한다.
4. 링크를 복원하고 경로 복귀 동작을 확인한다.
5. 300명 부하로 혼잡 임계값을 넘긴다.
6. 자동 경로 재계산 여부와 전환 후 처리량을 확인한다.

링크 장애와 혼잡 유발을 같은 실행에서 동시에 수행하지 않는다. 원인별 결과를
확보한 다음에만 복합 장애 시나리오를 추가한다.

## 측정 항목

### 사용자 관점

- 요청 수와 초당 요청 수(RPS)
- HTTP 상태 코드별 성공 및 실패 수
- 응답시간 p50, p95, p99
- 연결 실패, timeout, 재시도 수
- 로그인, 조회, 작성 행동별 성공률

### 애플리케이션 관점

- Mutillidae `www`와 DB 컨테이너 CPU 및 메모리
- DB 연결 수와 느린 요청
- 웹 access/error 로그
- TCP relay CPU, 연결 수, 오류 로그
- 컨테이너 재시작 횟수

### 네트워크 및 제어 관점

- OVS 포트별 bps, pps, drop, error
- Primary와 Backup 경로 상태
- 경로 재계산 요청 및 완료 시각
- 링크 장애부터 트래픽 복구까지 걸린 시간
- 설치, 제거, 만료된 Flow Rule
- Controller Packet-In 및 통계 처리량
- `sdn-sensor0` PCAP의 실제 원본 IP와 재전송 패킷

### 분석 파이프라인 관점

- Analyzer 처리 윈도우와 Backend 연결 상태
- Outbox pending, retry, dead-letter 수
- 패킷 요약과 보안 이벤트 전송 지연
- 정상 부하가 공격으로 잘못 탐지되는지 여부

## 초기 합격 기준

| 구간 | 기준 |
|---|---|
| 정상 100명 | HTTP 오류율 1% 미만, p95 1초 미만 |
| 정상 100명 | 인위적 장애가 없을 때 패킷 손실 0.5% 미만 |
| 정상 100명 | 의도하지 않은 보안 이벤트와 경로 변경 없음 |
| 피크 300명 | HTTP 오류율 2% 미만, p95 2초 미만 |
| 피크 300명 | Controller와 Analyzer 프로세스가 중단되지 않음 |
| 링크 장애 | Backup 경로 전환 후 트래픽이 다시 안정됨 |
| 복구 단계 | 100명으로 감소한 뒤 2분 안에 정상 지표로 복귀 |
| Analyzer | Backend 복구 후 Outbox pending 항목이 지속적으로 감소 |

스트레스 500명은 고정 합격 기준보다 최초 포화 지점과 장애 형태를 찾는 데
사용한다. CPU 90% 이상이 지속되거나, 메모리 부족, 컨테이너 반복 재시작,
오류율 급증이 발생하면 그 시점을 한계로 기록하고 실행을 중단한다.

합격 기준은 첫 기준선 결과를 얻은 뒤 하드웨어 성능과 실제 응답 크기에 맞춰
조정한다. 기준을 변경할 때는 이전 결과를 덮어쓰지 않고 변경 이유와 적용 시각을
남긴다.

## 실행 순서

1. Mutillidae DB를 기준 상태로 초기화하거나 snapshot을 복원한다.
2. Controller, Backend, Analyzer, Mutillidae 상태를 확인한다.
3. Mininet을 Sensor Mirror와 Mutillidae proxy 옵션으로 시작한다.
4. `h1`, `h2`, `h3`에서 `web:80` 연결을 확인한다.
5. `sdn-sensor0`에서 요청과 응답이 모두 보이는지 확인한다.
6. 프로필 A에서 준비, 정상, 피크, 스트레스, 복구 단계를 실행한다.
7. 결과를 저장하고 병목이 웹, DB, relay, 부하 생성기 중 어디인지 분류한다.
8. 상태를 복원한 뒤 프로필 B에서 링크 장애와 혼잡을 각각 실행한다.
9. 모든 Outbox 항목과 Flow Rule 수명주기가 정리됐는지 확인한다.
10. Mininet과 OVS를 정리하고 잔여 bridge가 없는지 확인한다.

공격 시나리오는 위 기준선이 확정된 이후 정상 사용자 100명을 유지한 상태에서
`h3` 트래픽을 별도로 추가한다. 공격을 포함한 결과는 일반 부하 결과와 같은
집계에 섞지 않고 별도의 실행 ID를 사용한다.

## 결과 보관 형식

각 실행에 고유한 ID를 부여하고 다음 구조로 결과를 보관한다.

```text
results/web-load/<실행-ID>/
  metadata.json
  load-generator.csv
  latency-summary.json
  docker-stats.csv
  ovs-port-stats.txt
  ovs-flows.txt
  controller.log
  analyzer.log
  web-access.log
  web-error.log
  sensor.pcap
  timeline.md
```

`metadata.json`에는 Git commit, VM 자원, 네트워크 프로필, 사용자 수, 증가 속도,
유지 시간, DB snapshot 식별자와 실행자를 기록한다. `timeline.md`에는 부하 단계,
링크 down/up, 경로 전환, 오류 급증처럼 서로 비교해야 하는 사건의 정확한 시각을
남긴다.

PCAP와 로그에는 세션 쿠키, 비밀번호, 게시글 데이터가 포함될 수 있으므로 외부에
공개하지 않는다. 테스트는 `sdn-lab`과 Mininet의 격리 주소만 대상으로 하며 외부
IP 또는 인터넷 서비스에는 부하나 공격 트래픽을 전송하지 않는다.
